Essentially, make sure the merge conflicts are resolved by integrating the This feature links the existing data collection voice agent to the flight search, display, and booking stages into a single cohesive pipeline. The pipeline has four sequential phases. Each phase has a clear input, a clear output, and a defined handoff to the next phase. The overall flow is: collect traveler identity and trip parameters via voice → search and display flights via a tool call defined in main → collect sensitive passenger details via voice or typed UI input → execute the booking. Critically, the pipeline has two possible entry points into Phase 1: the standard flow where the voice agent asks all fields from scratch, and the image flow where Gemini has already pre-populated certain fields like destination and suggested dates, and the voice agent uses those as a starting point rather than asking from scratch. Regardless of which entry point is used, Phase 1 always produces the same 8-field JSON object before Phase 2 begins.
Phase 1 — Identity and Trip Collection (Voice). The first voice agent converses with the user and collects exactly 8 fields: first_name, last_name, destination, origin, departure_date, return_date, num_passengers, and budget. This uses the existing store_travel_info tool-call mechanism and SSE session structure, with first_name and last_name added to the TRAVEL_FIELDS enum. In the standard flow, the agent asks for all 8 fields conversationally from scratch. In the image flow, the agent's system prompt is pre-loaded with Gemini-extracted context such as detected destination and suggested season, so it confirms pre-filled values with the user rather than asking blindly — for example saying "It looks like you're inspired by Bali, is that where you'd like to go?" rather than "Where would you like to go?" — but the agent still collects and stores all 8 fields through the same store_travel_info tool call regardless of whether the value was pre-suggested or user-provided. When all 8 fields are present, the session emits the existing all_fields_collected SSE event, and the output is a single JSON object containing all 8 fields stored on the session.
Phase 2 — Flight Search and Display (Tool Call from Main). The flight-finding function is defined and owned in main and is registered as a tool call that the server can invoke. When all_fields_collected fires, the server calls this tool with the following fields extracted from the Phase 1 JSON: departure_date, return_date, num_passengers, budget, origin, and destination. The tool queries the Duffel API, and its results are pushed to the frontend via a new flights_ready SSE event containing an array of flight offer objects. The frontend renders these as a selectable card UI. When the user selects a flight, the frontend posts the chosen offer_id to a new POST /api/select-flight endpoint, which stores it on the session and emits a flight_selected SSE event. Receipt of flight_selected is the trigger for Phase 3.
Phase 3 — Sensitive Passenger Detail Collection (Voice with UI Auto-Population). On flight_selected, the frontend automatically starts a second voice agent call using a new assistant config from GET /api/assistant-config-phase3. This agent collects 4 fields: phone_number, email, date_of_birth, and credit_card_number. All 4 fields are collected by voice in the same way — the user speaks the value, the agent transcribes it, auto-populates the corresponding UI input field in real time as the value is heard, and then reads the value back to the user for explicit verbal confirmation before calling store_passenger_info to save it. For example, when collecting a credit card number the agent says the digits back and asks "Is that correct?" before storing. This confirmation step applies to all 4 fields but is especially important for date_of_birth and credit_card_number. In parallel, the UI always renders active text input fields for all 4 values simultaneously, so the user can also manually type or correct any field at any point — for instance if they misspoke or prefer not to say a sensitive value aloud. Whether a value arrives via the store_passenger_info tool call from voice or via a POST /api/passenger-field HTTP call from the typed UI, both write to the same underlying session object and emit the same passenger_field_update SSE event, keeping the UI input and the voice-collected value in sync at all times. The completion check is identical regardless of input method. When all 4 fields are confirmed and stored, the server emits passenger_info_complete and the output is a JSON with phone_number, email, date_of_birth, and credit_card_number.
Phase 4 — Booking Execution. When passenger_info_complete fires, the server assembles the full booking payload by merging the Phase 1 session data (first_name, last_name) with the Phase 3 passenger data and the offer_id selected in Phase 2. This combined object is passed into the existing booking logic, which runs the create_payment_intent → card form display → confirm_payment → book_flight sequence exactly as previously specified. On success, the server emits a booking_confirmed SSE event containing booking_reference and order_id, and the frontend displays the confirmation and itinerary calendar.
